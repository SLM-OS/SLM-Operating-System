#1207: can a cache invalidate make a free-list header read as old DRAM content? And what else makes a listed block read zero?
Code reading at fix/pmm-coalesce 122befe0. Nothing here was run on hardware. QEMU TCG has no data cache to lose, so no
QEMU test can show or exclude any of this.
Second version (after round 2 of the review): the first one said every DC IVAC call site had been read (two were missed)
and treated a lost header write as possible on these boards without checking the tree's own record on it.

1. What the tree records about these cores

 - kernel/arch/arm64/mmu.S:46-50: "On Cortex-A76 and A78AE DC IVAC is executed as DC CIVAC, so a dirty stale line would be
   written back".
 - kernel/sched/smp.c:684-688: "Cortex-A76 / A78AE execute DC IVAC as DC CIVAC, which writes back this CPU's dirty line;
   architecturally an invalidate may discard it".
 - kernel/arch/arm64/smp_boot.S:205-213: "On these cores DC ISW is a local clean+invalidate, so the loop is harmless but
   not needed" (citing the A76 and A78AE TRMs and the #1193 audit).
 If that record holds, no DC IVAC or DC ISW on Pi 5 or Jetson can discard a dirty line, and a header the PMM wrote
 cannot be lost that way. I did not find the statement in docs/adr/0007-cross-cpu-coherency.md itself (no "IVAC", "ISW"
 or "discard" in it); the comments above are the record. A lost header write is therefore: architecturally possible,
 excluded on these cores if the in-tree record holds.

2. What survives

 A device that does not snoop the CPU caches writes DRAM under a line the CPU holds. If the CPU's copy is clean (the
 header was written back at some point, by eviction or by one of the invalidates above, which clean first), the CPU keeps
 reading its copy until the line leaves the cache and then reads what the device wrote. If the CPU's copy is dirty, the
 write-back overwrites the device's data instead. So a walk that first sees zeros bounds when the CPU's view changed, not
 when DRAM was written; and an invalidate that reaches the line (as clean + drop) is one of the ways the device's data
 becomes visible. That is the only role the call sites below can have on these cores.

5. Experiments (not run; the lab is down)

 The CVAC-and-pattern build proposed in the first version was meant to separate a lost write from a write of zeros.
 With section 1, a lost write is already excluded on these cores if the record holds, so that separation is worth less.
 What the build would still give:
 A. Stamp bytes 16..63 of each listed block's first line with a pattern derived from its address, and clean header and
    pattern to DRAM after every link write. On a finding the dump shows: pattern intact with zero or stale links (only the
    16 link bytes changed: a narrow write, or, against section 1, a lost header write); the whole line zero (a write of
    zeros at least 64 bytes wide, by a device or by the CPU); other data (a write of that data). It does not say when.
 B. To bound when DRAM changed: have the once-a-second walk drop its cached copy of each header line before reading it
    (DC CIVAC on the line; the copy is clean in build A, so nothing is written back). The walk then reads DRAM every
    second, and a finding's time bounds the DRAM write to that second. If findings then appear at boot or right after
    xhci_init rather than at the end of test_suite_gpu, the writer is a device left running by Linux; if they still appear
    only during test_suite_gpu, it is that suite's GPU activity.
 C. Independently: print every reserved range and hand-off buffer address, and walk the lists after each test of
    test_suite_gpu.
 About 30 kexec suite boots each; at a true rate of 0.15, 30 boots without a finding have probability 0.008.
