#1207: can a cache invalidate without write-back (DC IVAC) make a free-list header read as old DRAM content?
Code reading at fix/pmm-coalesce 02ebdad8. Nothing here was run on hardware. QEMU TCG has no data cache to lose, so no
QEMU test can show or exclude this.

The idea (from the review of this branch). A header the PMM wrote can stay dirty in the CPU cache for a long time; the
blocks at and near the head of a list are the ones rewritten most recently (every free_list_add rewrites the old head's
prev link). A DC IVAC that reaches such a line discards it, and the next read returns what DRAM held before: on a kexec
boot, whatever Linux left in that page. That is a lost CPU write with no writer in the window, and it would look exactly
like boot 04 (a listed block reading zero, block_state still "listed"). The same picture results if a device that does
not snoop the CPU caches wrote DRAM earlier and the cached copy was dropped later. Either way the walk that first sees
zeros bounds when the CPU's view changed, not when DRAM was written.

What stays open regardless of the call sites: the first case above needs no IVAC call at all. Any way a dirty line leaves
the cache without being written back, or a device writing DRAM under a line the CPU holds, gives the same capture.

Experiments that separate "lost write / stale DRAM" from "a write of zeros" (not run; the lab is down):
 A. Write every header through to DRAM: DC CVAC on the header's line after each link write in free_list_add,
    free_list_remove and free_list_pop (diagnostic option). A later discard can then only restore the header itself.
    If the halt rate stays at 1 to 2 in 10 over about 30 kexec suite boots, a write of zeros reaches the block; if it goes
    to 0 in 30 (probability 0.008 at a true rate of 0.15), the class is lost writes or stale DRAM.
 B. In the same build, stamp bytes 16..63 of each listed block's first line with a pattern derived from its address and
    clean it to DRAM. On a finding the dump then shows which it was: pattern intact with stale links (a lost write),
    all zero (something wrote zeros), or other data (something wrote that data).
 C. Independently of A and B: print every reserved range and hand-off buffer address, and walk the lists after each
    test of test_suite_gpu, to name the test.
