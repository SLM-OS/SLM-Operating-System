What follows from the observations
 - The block was intact after test_suite_oplib_gpu_as and damaged by the end of test_suite_gpu: the write happened during
   test_suite_gpu. This is the first time the damage is bracketed.
 - It is not the xHCI hand-over window (that ended before the first suite, and every walk until the GPU suite was clean).
 - The data written is zeros, over at least the last 64 bytes of one 64 KB block and the first 64 of the next.

Inferences (not shown)
 - The writer is the MNIST GPU path that the last tests of the suite start on the inherited channel (the bring-up line is
   the only GPU activity in that suite's log): either the GPU writing through its own page tables into a physical page
   that the hand-off reservation does not cover, or SLM-OS code on that path clearing a buffer whose address or length
   comes from the hand-off page. A 64 KB-aligned 64 KB block is the size and alignment of the GA10B hand-off's own
   buffers (both pushbufs are 65536-byte ranges at 64 KB-aligned addresses), which fits "one more buffer of the same
   allocation family that is not in the reserve list"; not verified.
 - Whether the once-a-second tick walk runs on this board was not checked separately (the finding came from the suite
   boundary walk); if it does, the write fell in the last second of the suite, which is where those tests are.
 - Why only some boots: the write must land on the first 16 bytes of a block that is on a free list, and a later
   allocation must reach it; where Linux put the hand-off buffers differs every boot. Not verified.
 - The three earlier halts of this session (f55c5293 boot01 order 7, boot05 order 5; here order 4) and the older captures
   are consistent with the same writer; only this one has the bytes.
