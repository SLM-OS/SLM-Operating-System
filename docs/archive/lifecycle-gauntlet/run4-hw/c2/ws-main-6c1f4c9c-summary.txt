## Class A (#1219): mechanism from the samples

What the stress test waits on: rust_infer_stress_run's join loop on
main (CPU 0) waits for STRESS_WORKERS_DONE >= 4. At the FAIL line it is
0 of 4 with STRESS_SUCCESS 0 and STRESS_ERROR 0 (run05, run08, run17,
t3): no worker completed even one inference.

PCs (all 4 vCPUs, both sample points, run05, run08, run17, t3): every
vCPU is at 0x4023f794 / 79c / 7ac / 7b0, the ldaxrb/clrex/isb loop on
ENGINE_LOCK (0x4203680c) inlined at the top of
slm_runtime::inference::engine::run_inference_inner (engine_lock(),
runtime/src/inference/engine.rs:469). CPUs 1 to 3 run three
infer-stress workers; CPU 0 runs main, which by 100 s has moved on to
"[TEST] Inference FFI Tests" and spins on the same lock (that is why the
suite then hits the 120 s cap). The remaining samples are the EL1h IRQ
vector (0x40010a80): the spinners take IRQs, PSTATE 0x60000005 (DAIF
clear) in 16 to 19 of the 20 readings per CPU (run05, run08, run17).

The holder (run17 and t3, which have the extended dump): ENGINE_LOCK
byte = 1, SCHED_LOCK = 0, SCRATCH_LOCK = 0. The fourth infer-stress task
is READY, never running again (sw=1), its frame chain is schedule+576
<- el1_irq+164 (switched out by a timer IRQ, not by a yield). In t3 its
trap frame holds ELR 0x4022cd2c (slm_runtime::inference::ops::conv2d +
1000), SPSR 0x5: it was preempted inside an inference, holding
ENGINE_LOCK. t3 RQ lines: it is the head of CPU 2's run queue
(ready_count=1), not lost.

Why CPU 2 never switches back to it (t3, two dumps 13 s apart, at 87 s and 100 s):
`DIAG preempt_disabled=[0, 0, 1, 0]` in both;
sched_diag_tick[2] 7209 -> 7941 while sched_diag_schedule[2] stays at
15244. CPU 2 takes its 100 Hz ticks but scheduler_tick() returns at
`if (preempt_disabled[cpu]) return;` (kernel/sched/sched.c:2722), so
the spinner on CPU 2 is never preempted. sched_try_steal() skips a
victim whose preempt_disabled is set (sched.c:1868), so no other CPU
takes the holder either. preempt_disabled[2]=1 while CPU 2 runs a task
outside schedule() is itself the defect: the flag is supposed to be set
only inside schedule()'s switch window.

Hypothesis (code reading, not yet tested): schedule() computes
`this_cpu = cpu_id()` on entry (sched.c:2314), sets
preempt_disabled[this_cpu] = 1 (:2464), calls switch_to (:2530), and
after switch_to returns clears preempt_disabled[this_cpu] (:2534) with
the pre-switch id. Under CONFIG_WORK_STEALING a READY task can be
stolen and resumed on another CPU; when it returns from switch_to there,
it clears the old CPU's flag and leaves its new CPU's flag set until
that CPU's running task calls schedule() voluntarily. A spin-waiter that
never yields (engine_lock) then deadlocks against a lock holder parked
on that CPU's queue. In t3, CPU 2's current task (infer-stress slot 13,
sw=2, last saved in schedule) is consistent with having resumed through
that tail. The same stale store also clears another CPU's flag while
that CPU may be inside its own switch window, which is the window
#1216 says the early-out protects. Whether that contributes to #1213 is
a separate hypothesis, not tested here. Confirming experiment: re-read
the CPU id after switch_to (or record which CPU set the flag) and
re-run this cell; rate to 0 under the 5x rule.

Classification: not C1's mechanism as stated for #1213 (no fault, no
slot reuse, no CPU wedged in an exception); a lock holder stranded on a
CPU whose preempt_disabled flag is stuck at 1. Kernel code, not test
code: filed as #1229, not fixed.

The digit_classifier "Exiting (0 inferences)" line that precedes the
FAIL in every class A run (and both run-3 failures) is that component's
30 s inactivity timeout (kernel/src/component_runtime.c:415); the
failed join itself waits 30.8 s, so the exit follows from elapsed time.
Not causal as far as these samples show.
