# x86-64 Gap Closure Plan: Preemption, SMP, GPU Inference

**Companion to:** [docs/x86-64-capstone-gaps.md](x86-64-capstone-gaps.md)
**Last updated:** 2026-04-13
**Scope:** Concrete, file-level plan to close every gap identified in the
capstone gap analysis — preemptive multitasking, SMP, and GPU-backed
model inference on x86-64.

Each workstream below specifies:
- **Deliverables** — exact files and symbols to add or change.
- **Design** — API shape, invariants, and integration points.
- **Tests** — regression tests that must pass.
- **Acceptance criteria** — observable gates before the workstream closes.
- **Est.** — engineer-days.

Every workstream lands as a separate PR unless it is explicitly labelled
(grouped). Each PR must merge clean against `main` with the
Claude-Code-Review check green and no regressions in ARM64 / QEMU
x86-64 / test-pc hardware test suites.

## Phase A — Preemption hardening

Goal: remove two safety / confidence gaps so the preemption code path is
bulletproof under real-hardware, adversarial workloads.

### A1. TSS + per-CPU IST stack for the LAPIC timer vector (P1-1)

**Deliverables.**
- New file: `kernel/arch/x86_64/tss.c` — builds one TSS per CPU.
- New field in `kernel/include/smp.h` `struct per_cpu`:
  `uint8_t ist1_stack[4096] __attribute__((aligned(16)));`
- New entry in the GDT (currently defined inline in
  `kernel/arch/x86_64/trampoline32.S`): a 16-byte TSS descriptor at
  selector 0x28. Since the GDT is shared across CPUs, each CPU
  rewrites the TSS base pointer in-place before `ltr` on that CPU.
- Modify `kernel/arch/x86_64/idt.c:idt_init()` — IDT entry for
  vector 48 sets `ist = 1` (the other vectors keep `ist = 0`).
- In `platform_x86.c:kernel_main_x86()` (BSP) and
  `platform_x86.c:ap_entry_64()` (APs): call a new
  `tss_install_current_cpu()` that writes the TSS descriptor, sets
  `rsp0` (kernel-stack pointer, unused today but needed for future
  ring-0↔ring-3 transitions), sets `ist[0]` (→ `ist1_stack` top), and
  issues `ltr $0x28`.

**Design.**
- One TSS per CPU, stored in `cpu_data[i].tss` (new field, 104 bytes).
- Each TSS has `IST1 = &cpu_data[i].ist1_stack[4096]` (stack grows
  down from the high end).
- Only vector 48 uses IST1. Exceptions keep the legacy
  "current-stack" behaviour because they can be synchronously
  generated by the task and need the task's stack for
  `handle_double_fault`-style recovery (deferred: if we need a
  double-fault IST, add IST2 in a follow-up).

**Tests** (`kernel/tests/test_x86_boot.c`, new):
- `test_tss_loaded` — reads the task register (`str %ax`) and asserts
  selector == 0x28.
- `test_tss_per_cpu_distinct` — each CPU reads its own TSS base via
  `sgdt` + selector decode; asserts all 8 bases are distinct.
- `test_timer_isr_uses_ist1` — before firing a timer IRQ, record
  `cpu_data[cpu_id()].ist1_stack[4095]`; install a short-term timer
  hook that stashes the top 8 bytes of its stack; after the tick,
  assert the stash landed inside `ist1_stack[...]` (i.e., the ISR
  ran on IST1).
- `test_task_stack_overflow_does_not_corrupt_isr` — a task
  deliberately writes guard-byte patterns around its stack base;
  asserts the ISR frame never appears inside the task's stack page.

**Acceptance criteria.**
- All 4 new tests pass in QEMU and on test-pc.
- No regression in the existing 10 SMP tests.
- `objdump -d slmos.elf | grep ltr` shows one call per CPU bringup.

**Est.** 2 days.

### A4. TSC-based `sleep_ms()` (P1-4)

**Deliverables.**
- Rewrite `sleep_ms()` at `kernel/arch/x86_64/timer_x86.c:145-152` to
  use the already-calibrated TSC via `timer_get_count()` +
  `timer_get_frequency()` instead of polling the BSP-only
  `pit_ticks` counter. Concretely:

  ```c
  void sleep_ms(uint32_t ms)
  {
      if (ms == 0) return;
      uint64_t freq_hz = timer_get_frequency();      // ~1 GHz TSC
      uint64_t target  = timer_get_count() + (uint64_t)ms * freq_hz / 1000;
      while (timer_get_count() < target)
          yield();
  }
  ```

- `timer_get_count()` already returns `rdtsc()` when `tsc_freq > 0`
  (`timer_x86.c:125-130`), so every CPU's `sleep_ms` is now driven
  by a per-CPU TSC instead of a cache-coherent global `pit_ticks`
  write from BSP.
- Leave `pit_ticks` intact for existing BSP-only uses (shell
  uptime, scheduler diagnostics).

**Why this moves to Phase A.** Phase C benchmarks `sleep_ms`-gated
inference workloads. If any benchmark task ends up on an AP (via
future work-stealing or explicit affinity) the pre-fix `sleep_ms`
would add up to a 10 ms jitter floor to every measurement. Landing
the TSC fix before Phase C makes all subsequent measurements
trustworthy regardless of which CPU executes them.

**Tests** (`kernel/tests/test_x86_boot.c`):
- `test_sleep_ms_on_bsp` — `sleep_ms(100)` returns within [100, 115] ms
  on BSP. (Tightens an existing bound.)
- `test_sleep_ms_on_ap` — spawn a task pinned to CPU 3, have it
  `sleep_ms(100)`, assert it returns within [100, 115] ms. Fails
  pre-fix (returns in 0–10 ms intervals due to `pit_ticks` skew);
  passes post-fix.

**Acceptance criteria.**
- Both tests pass in QEMU and on test-pc.
- No regression in existing timer tests.

**Est.** 1 day.

## Phase B — SMP responsiveness

Goal: make cross-CPU dispatch real-time (≤1 ms) and prove per-CPU
preemption with a specific test.

### B1. Reschedule IPI (P2-1, P2-5, P1-3)

**Deliverables.**
- New LAPIC vector constant: `#define RESCHED_VECTOR 0xF1` in
  `kernel/arch/x86_64/lapic.c` (chosen: high-priority IPI, above the
  IOAPIC range 32–47 and the LAPIC timer at 48).
- New ISR stub in `kernel/arch/x86_64/idt.S` and IDT entry for
  vector 0xF1 with `ist = 1` (shares IST1 with the timer — same
  preemption semantics).
- New handler in `kernel/arch/x86_64/platform_x86.c`:
  ```c
  static void resched_ipi_handler(uint8_t vec) {
      (void)vec;
      /* Force a reschedule on this CPU. The IPI woke us out of
       * hlt; returning from the ISR without calling schedule()
       * would drop us back into the idle loop and we'd have to
       * wait for the next LAPIC timer tick (~10 ms) to notice
       * the new task the sender just queued. We call schedule()
       * directly — NOT scheduler_tick() — because the latter
       * also advances quantum accounting / AI telemetry /
       * per-CPU running_ticks counters, and doing that on every
       * resched IPI would double-tick quota and corrupt the
       * fairness policy. The LAPIC timer remains the sole
       * source of "a tick happened"; IPI just requests an
       * immediate switch opportunity. */
      schedule();
  }
  ```
  Registered via `irq_register(RESCHED_VECTOR - 32, resched_ipi_handler)`
  (note: vector 0xF1 is above 47 so it does not collide with the
  IOAPIC table). The standard `preempt_disabled[cpu]` reentrance
  guard in `schedule()` still protects the critical window — if the
  IPI fires while `schedule()` is already in flight on this CPU, the
  inner `schedule()` no-ops (see `sched.c:1041`).
- **Reuses the `smp_notify_cpu(uint32_t logical_cpu)` API** landed
  in infrastructure PR Pre-1. B1 fills in the x86-64 backend;
  ARM64's backend (`sev`) already exists. Common caller sites —
  `scheduler_add_task_to_cpu()`, work-stealing remote-wakeup — use
  the same symbol on all platforms, so B1 does not re-touch
  `sched.c`.
- New implementation of the x86-64 backend in
  `kernel/arch/x86_64/platform_x86.c`:
  ```c
  /* x86-64 backend for smp_notify_cpu (declared in smp.h). */
  void smp_notify_cpu(uint32_t logical_cpu) {
      if (logical_cpu == cpu_id()) return;
      uint32_t apic_id = cpu_data[logical_cpu].mpidr;
      lapic_send_ipi(apic_id, RESCHED_VECTOR, ICR_FIXED);
  }
  ```
- `kernel/sched/sched.c:scheduler_add_task_to_cpu()` already calls
  `smp_notify_cpu()` after Pre-1 lands (ARM64 arm = `sev`, x86-64
  arm = undefined until B1). B1 just adds the missing implementation
  — no scheduler edits, no `#ifdef PLATFORM_X86_64` sprinkling.

**Design.**
- The IPI unblocks an idle AP from `hlt`. On return from ISR, the
  AP falls into `scheduler_tick()` → `schedule()`, which pulls the
  new task from its run queue.
- We share IST1 with the timer vector because both are "preemption
  triggers". If we later need per-IRQ IST stacks, add them then.
- Rate-limit: no software limit, but the runqueue-empty check
  prevents IPI storms during burst dispatch.

**Tests** (`kernel/tests/test_x86_boot.c`):
- `test_resched_ipi_delivers` — BSP calls `smp_notify_cpu(1)`;
  verifies a counter in the IPI handler incremented within 1 ms.
- `test_cross_cpu_dispatch_latency` — BSP creates a task pinned to
  CPU 7; measures wall-clock time (via `rdtsc`) from
  `scheduler_add_task()` to the task's first-instruction counter
  increment; asserts < 1 ms on real hardware, < 5 ms in QEMU.

**Acceptance criteria.**
- Both new tests pass.
- No regression in the existing 10 SMP tests.
- `bench smp` on test-pc shows all 8 CPUs picking up work within
  1 ms of dispatch (measure via per-CPU rdtsc timestamp at task
  entry).

**Est.** 3 days.

### B3. Enable and validate `CONFIG_WORK_STEALING` (P2-3)

**Deliverables.**
- Do **not** flip the global default in `kernel/include/config.h:40`.
  Per the cross-platform review, each platform opts in independently
  until benchmark data from ≥ 2 platforms justifies the shared flip:
  - x86-64: `CMakeLists.txt` passes `-DCONFIG_WORK_STEALING=1` only
    when `PLATFORM=X86_64`.
  - Jetson S4 decides its own value based on its Gate-2 bench.
  - Pi 5 keeps it off until its IRQ blocker lands.
  `config.h:39-40` stays `#ifndef CONFIG_WORK_STEALING; #define
  CONFIG_WORK_STEALING 0; #endif` so the CMake override wins.
- **Audit the existing lock discipline** (primary defense). The
  current `sched_try_steal()` at `sched.c:1077-1110`:
  1. Calls `steal_deque_steal()` which holds the deque's own
     `spin_lock_irqsave(&d->lock)` for the entire pop operation
     (`steal_deque.c:76-89`).
  2. Acquires the **victim's** `rq_lock_irqsave(victim)` before
     validating `state == TASK_READY && assigned_cpu == victim &&
     cpu_affinity == CPU_AFFINITY_ANY` and calling
     `remove_from_cpu_queue_locked(candidate, victim)`.
  3. Releases both locks before returning the candidate.

  The victim's `rq_lock` is the same lock its own `schedule()`
  takes at `sched.c:~1030` when running `pick_next_task` +
  `task_set_current` + `preempt_disabled = 1`. So the steal window
  is already mutually excluded from the victim's `schedule()` —
  the race the original plan was worried about cannot happen, and
  the `preempt_disabled` check is redundant with the `rq_lock`.
- **Belt-and-suspenders**: additionally skip a victim if
  `preempt_disabled[victim] != 0` at the top of the loop, as a
  cheap early-out that avoids contending a lock a victim CPU is
  almost certainly about to hold itself. This is **defence-in-depth**,
  not the primary correctness argument.
- Add `bench smp --work-stealing` shell command that measures tail
  latency under an 8×CPU-bound workload with and without stealing.

**Tests.**
- `test_work_stealing_rebalance` — create 8 long-running tasks all
  pinned nowhere (CPU_AFFINITY_ANY), assert that within 100 ms all 8
  CPUs show `sched_diag_running[i] > 0`.
- `test_work_stealing_respects_preempt_disabled` — a CPU with
  `preempt_disabled=1` is never stolen from (asserts by hooking the
  steal path with a counter).

**Acceptance criteria.**
- Both tests pass.
- `bench smp` with work-stealing on shows measurably better tail
  latency (p99 ≤ 1.5× p50) than with work-stealing off.
- No regression in any existing scheduler test.

**Est.** 2 days.

## Phase C — x86-64 SIMD inference (P3-1)

Goal: close the 2–3× slowdown on x86-64 inference without triggering the
LLVM soft-float legalizer bug tracked in #72.

### C1. Inline-assembly SSE matmul

**Deliverables.**
- **Depends on infrastructure PR Pre-2** (SIMD dispatch skeleton).
  Pre-2 lands empty `x86_64` and `aarch64` arms in every dispatch
  wrapper; C1 fills the `x86_64` arm. The Jetson plan's G1 fills
  the `aarch64` arm on the same timeline. No further changes to
  `matmul()`, `relu()`, `zero_buf()`, `add_scalar_simd()`,
  `simd_fma_row()` dispatch shape are needed — only the inner
  kernels.
- Four new `unsafe fn`s in `runtime/src/inference/ops.rs`, gated on
  `#[cfg(target_arch = "x86_64")]`, invoked from the Pre-2
  skeleton's `x86_64` arm:
  - `relu_sse2_asm(inp: *const f32, outp: *mut f32, n: usize)`
  - `zero_buf_sse2_asm(ptr: *mut f32, n: usize)`
  - `add_scalar_sse2_asm(ptr: *mut f32, scalar: f32, n: usize)`
  - `simd_fma_row_sse2_asm(cp, bp, scalar, n)`
- Each uses Rust `asm!` blocks with explicit `xmm0..xmm3` register
  clobbers. **No `core::arch::x86_64` intrinsics** — those trigger
  the LLVM `Do not know how to split the result of this operator!`
  crash documented in #72.
- The asm blocks use only SSE/SSE2 instructions (`movups`, `maxps`,
  `mulps`, `addps`, `xorps`, `shufps`, `movaps` where alignment is
  guaranteed by the caller).

**Design.**
- **Why inline asm works where intrinsics don't**: inline `asm!`
  block arguments are just registers — they never carry an `__m128`
  Rust type through the type system, so LLVM's soft-float legalizer
  never sees a vector `return` or vector `store` that it needs to
  "split the result" of. The instructions still execute correctly
  because the `x86_64-unknown-none` target's actual CPU (i7-6700)
  has SSE unconditionally.
- **Enabling CR4.OSFXSR**: required by the hardware for any
  `movups`/`maxps` at CPL 0. Set in `trampoline32.S` and
  `ap_trampoline.S` as part of C1 (restoring the CR4/CR0 flags that
  were rolled back at the end of PR #103).
- **Stack alignment**: inline asm doesn't change the ABI, so no risk
  of the `movaps` at misaligned `r13+0x40` crash that Path C hit in
  #72's investigation. We use only `movups` (unaligned) in the
  generated code.
- **Alternative considered**: `#[target_feature(enable = "sse2")]`
  on inner `unsafe fn`s — still triggers the legalizer crash because
  function boundaries in Rust carry typed SSE return values.

**Concurrent-SSE invariant (Phase C scope).** Phase C runs inference
on a single task at a time (shell-driven `bench infer` /
`rust_infer_classify`). Only that one task touches XMM registers.
The kernel itself is built with `-mno-sse`, so the timer ISR, IPI
handler, and every other preemption path do not clobber XMM state.
This means preemption of the inference task by timer or IPI is
**safe without FXSAVE/FXRSTOR**: XMM state sits in the SSE register
file, and when the task resumes it finds its XMM registers exactly
as it left them.

As soon as a second task uses SSE concurrently — Phase D's
`bench infer` parallel runs, or any future multi-tenant inference —
the `switch_to` sequence in `kernel/arch/x86_64/context.S:34-82`
becomes unsafe because XMM state is neither saved nor restored.
**Tracked in this plan as P1-6 / Phase D (D3 below).** The Phase C
PR must not claim "multi-task SSE" as a supported configuration
until D3 lands.

**Tests.**
- Mirror the existing ARM64 ops tests in
  `runtime/src/inference/ops.rs` (tail tests for `relu`, `matmul`,
  etc.). Run on `x86_64-unknown-none` release build.
- Add `bench infer` comparison in the shell: run MNIST classify
  N=100 times, measure average latency, print scalar vs SIMD.

**Acceptance criteria.**
- `cargo build --target x86_64-unknown-none --release` passes
  without `rustc-LLVM ERROR`.
- MNIST inference latency on test-pc improves ≥2× over the scalar
  baseline recorded in `docs/benchmarks.md`.
- Numerical output of every op matches the scalar path bit-exactly
  (unit test: `test_sse_matches_scalar`).

**Est.** 4 days.

### C2. Update CR4/CR0 setup to match C1

**Current state (verified against `main`, commit d64de4e).** Neither
`trampoline32.S` nor `ap_trampoline.S` touches CR0.EM, CR0.MP,
CR4.OSFXSR, or CR4.OSXMMEXCPT today — they only set CR4.PAE and
CR0.{PE, PG}. EM/MP/OSFXSR therefore hold whatever values the
bootloader or firmware left. On GRUB + OVMF they happen to land in a
workable default (EM=0, MP=1, OSFXSR=0), which is why the current
kernel doesn't fault on SSE-emitting code that slipped past
`-mno-sse` (e.g., Lua's `lmathlib.c` built with `-msse -msse2`). But
"workable default" is not a guarantee; PR #103 rolled back a
defensive change here after the SSE experiment didn't pan out, and
the current kernel is relying on firmware luck.

**Deliverables.**
- `kernel/arch/x86_64/trampoline32.S`: after enabling PAE, add:
  ```
  /* CR4 |= OSFXSR (bit 9) | OSXMMEXCPT (bit 10) */
  mov %cr4, %eax
  or  $0x600, %eax
  mov %eax, %cr4

  /* CR0: MP=1 (bit 1), EM=0 (bit 2) — required for SSE */
  mov %cr0, %eax
  and $~0x4, %eax          /* clear EM */
  or  $0x2,  %eax          /* set   MP */
  mov %eax, %cr0
  ```
- Mirror the same sequence in `kernel/arch/x86_64/ap_trampoline.S`
  so APs also enable SSE at CPL 0.
- **Verify before the change lands**: `grep '%cr0' kernel/arch/x86_64/*.S`
  — confirm no other site sets EM or clears MP later in boot.

**Tests** (kernel-level, in `test_x86_boot.c`):
- `test_cr4_osfxsr_enabled` — asserts `CR4 & 0x200 != 0` (OSFXSR).
- `test_cr4_osxmmexcpt_enabled` — asserts `CR4 & 0x400 != 0`.
- `test_cr0_em_clear_mp_set` — asserts `(CR0 & 0x4) == 0` and
  `(CR0 & 0x2) != 0`.

## Phase D — SMP rebalance + SSE polish

Goal: eliminate load imbalance (D1) and close the last concurrency
gap introduced by Phase C (D2). D2 becomes a hard prerequisite for
any workload that runs two SSE-using tasks concurrently — notably
parallelised inference in Phase E.

### D1. Periodic scheduler rebalance (P2-4)

**Deliverables.**
- New file: `kernel/sched/sched_rebalance.c` — owns a per-Nth-tick
  hook installed via `active_policy->tick()`.
- Algorithm: every 100 ticks, compute load stdev across all CPU run
  queues (via `cpu_rq(i)->ready_count`). If stdev > 1.5× mean,
  migrate one task from the busiest CPU to the idlest CPU.
- Migration itself is "dequeue from source, requeue on destination,
  IPI the destination via `smp_resched_cpu()`" (reuses B1).
- Respects `task->cpu_affinity` — tasks with explicit affinity are
  never migrated.

**Tests.**
- `test_rebalance_after_burst` — create 16 tasks on CPU 0 in a
  burst, then sleep 200 ms, then assert that at least 4 CPUs have
  nonzero `ready_count`.
- `test_rebalance_respects_affinity` — pin one task to CPU 0; create
  7 more tasks on CPU 0; assert that the pinned task is still on
  CPU 0 after rebalance.

**Est.** 4 days.

---

### D2. FXSAVE / FXRSTOR in `switch_to` (P1-6)

**Deliverables.**
- Extend `struct cpu_context` in `kernel/include/task.h`: append a
  512-byte `alignas(16) uint8_t fxsave[512]` buffer after `rflags`.
  Update `CTX_*` offset defines in `kernel/arch/x86_64/context.S`
  to match and assert the new size with `_Static_assert`.
- Update `switch_to` at `kernel/arch/x86_64/context.S:34-82`:
  - Save path: `fxsave (RDX + CTX_FXSAVE)` before the `pop %rax` /
    RFLAGS save. Use plain `fxsave` (not `fxsaveq` or `xsave`) —
    Phase C only relies on SSE, and `fxsave` covers x87 + MMX + XMM
    in a single instruction on every x86-64 processor.
  - Restore path: `fxrstor (RDX + CTX_FXSAVE)` before the
    `mov rflags` restore.
- Initialise the FXSAVE area for new tasks in
  `kernel/sched/task.c:task_create`: `memset(&task->context.fxsave, 0,
  sizeof(task->context.fxsave))` and set the `FCW` field
  (`fxsave[0..2]`) to `0x037F` (x87 control word default, matches
  the i387 init state per Intel SDM Vol. 1 §8.1.5).
- Update the `task_stack_within_mapping`-style tests that hardcode
  the context size to use `sizeof(struct cpu_context)` instead of a
  literal.

**Design.**
- Size is exactly 512 bytes (FXSAVE area). Alignment is 16-byte
  (FXSAVE requires it). The entire `struct cpu_context` must
  therefore be 16-byte aligned — verify with `_Static_assert
  (alignof(struct cpu_context) >= 16)`.
- `fxsave` clobbers the memory operand but not registers, so the
  assembly save sequence doesn't need extra scratch.
- **Why not `xsave`**: `xsave` saves AVX/AVX2 state in addition to
  SSE, but the x86-64 kernel and runtime currently only use
  SSE/SSE2. Switching to `xsave` is a one-line change when AVX
  support lands (Phase E or later).

**Tests** (`kernel/tests/test_x86_boot.c`):
- `test_context_has_fxsave` — assert
  `sizeof(struct cpu_context) >= old_size + 512`.
- `test_fxsave_preserves_xmm_across_preemption` — two tasks, each
  loads a distinct XMM pattern (via inline asm), yields, reads it
  back, asserts unchanged. This test fails today (XMM state shared
  between tasks), passes post-D2.
- `test_fxsave_new_task_fresh_fcw` — new task reads FCW via
  `fstcw`, asserts `0x037F`.

**Acceptance criteria.**
- All 3 tests pass.
- `make test` on ARM64 still passes (no cross-platform regression).
- `make x86-disk-verify` still passes (BPB and disk invariants
  unchanged).

**Est.** 2 days.

## Phase E — GPU compute via GSP-RM (post-capstone)

Goal: boot the RTX 3050's GSP-RM microcontroller, establish an RPC
channel, submit compute kernels, and back `gpu_execute_matmul()` with a
real GPU path.

This phase is **out of capstone scope** but included for completeness.
It is the largest single workstream in the plan and requires access to
the NVIDIA GSP firmware blob (normally on a Jetson's `/lib/firmware/`
or extracted from a GeForce driver package).

### E1. Firmware acquisition and packaging

**Deliverables.**
- Extract `gsp-535.113.01.bin`, `booter_load.bin`, and
  `booter_unload.bin` from the NVIDIA open-gpu-kernel-modules release
  (already in `../slmos-reference-cache/nvidia/nvidia-open-gpu-kernel-modules/`? —
  audit first).
- Verify signatures against NVIDIA's published hashes.
- Commit a compressed copy (or a `build.rs`-driven download) to
  `runtime/firmware/ampere/`.
- Decide: embed firmware in kernel image (simplest, +38 MB) or load
  from FAT ESP at runtime (adds filesystem code to the boot path).

**Design decision to make.**
- **Embed**: simplest, debuggable, but bloats `slmos.elf` by 38 MB
  and disk image by similar.
- **Runtime load**: requires early littlefs/FAT access before PMM —
  currently not wired up on x86-64.
- **Recommendation**: embed for initial bringup; move to runtime
  load as a polish step.

**Est.** 2 days (once firmware access is secured).

### E2. VBIOS parser (P3-3) — **DONE**

**Shipped.**
- Shared parser: `kernel/gpu/nvidia/nvidia_vbios.{h,c}`. The parser
  is platform-agnostic — both x86-64 bare-metal and Jetson can link
  it. (Original plan called for `kernel/arch/x86_64/nvidia_vbios.c`;
  refactored during implementation per the "share as much as
  possible across platforms" directive.)
- x86-64 platform loader: `nvidia_vbios_platform_load()` lives in
  `kernel/arch/x86_64/nvidia_gsp_platform.c`. Reads the expansion
  ROM via PCI Config Space ROM BAR toggle (save, enable, copy,
  restore), handing the raw bytes to the shared parser.
- Linux harness loader: `nvidia_vbios_platform_load()` in
  `host-tools/gsp-harness/linux_platform.c` reads via
  `/sys/bus/pci/devices/<BDF>/rom` (same `echo 1 > rom` dance).
- BIT table parser handles:
  - Signature detection (0x55AA PCI ROM, `0xFFB8 BIT\0`).
  - Defensive bounds (hdr_size ≥ 12, entry_size = 6,
    num_entries ≤ 64, entry offsets within image).
  - Lookup by `(id, version)` incl. wildcard version.
- FWSEC (BIT id 0x85): `nvidia_vbios_get_fwsec()` returns the
  ucode pointer + length for Turing+. Returns `-1` on Pascal
  (expected — no FWSEC entry).

**Wired into the GSP vtable.**
`struct gsp_platform_ops::vbios_get_fwsec` is live on both
platforms — the shared GSP bringup code calls into the platform
loader without knowing which one it is.

**Tests.**
- `make test-vbios` — 9 synthetic-image tests covering good parse,
  bad PCI signature, missing BIT, malformed entry_size, over-cap
  num_entries, entry off-end, find_entry by id+version, FWSEC
  extraction, FWSEC absent (Pascal layout). All pass.
- Validated against a real GTX 1070 VBIOS dump: 17 BIT entries,
  bit_offset=0x1e0, FWSEC absent as expected on Pascal.
- Real RTX 3050 validation (Turing+ FWSEC path) deferred to
  test-pc once the Linux/VFIO harness is online.

**Actual:** ~1 day.

**Shipped follow-up (worktree-x86-64-capstone-gap-work):**

- **E3.4 (FWSEC bug audit)** — Code-review pass against nouveau and
  nova-core sources surfaced two bugs in the FWSEC-FRTS path that
  match the symptom "ucode runs but never halts":
  1. `falcon_hs_boot()` was passed `imem_virt_base` as the boot
     vector. Both `nvkm_gsp_fwsec_v3` and nova-core's
     `FwsecFirmware::boot_addr()` hard-code BOOTVEC=0 for FWSEC v3.
     A non-zero BOOTVEC starts the Falcon at a stale VA and the
     ucode runs into garbage. Fixed in `bringup.c`.
  2. `falcon_start()` always wrote `CPUCTL` (0x100). nova-core
     checks `CPUCTL.ALIAS_EN` (bit 6) and uses `CPUCTL_ALIAS`
     (0x130) when set — required after the BROM hands off. Fixed
     in `falcon.c`.
  Hardware re-test required to confirm WPR2 now populates.

- **E3.4.d** — Booter Load on SEC2. New PIO IMEM/DMEM upload
  helpers (`falcon_pio_upload_imem` / `falcon_pio_upload_dmem`)
  matching `gm200_flcn_fw_load`'s loader path used by booter on
  GA10x. `gsp_bringup_booter_load()` parses `booter_load-535.113.01.bin`
  via nvfw, builds a DMA-mapped mutable copy with signature 0
  patched into DMEM, programs SEC2 BROM, hands MAILBOX0/1 the
  WprMeta phys addr, kicks STARTCPU, polls halt. WprMeta is
  zero-initialized at this milestone (the booter halts with a
  non-zero MAILBOX0 status without a populated WprMeta — the halt
  itself is the deliverable; full WprMeta layout is owned by E4).

- **E3.4.e** — GSP RISC-V bringup. `gsp_bringup_riscv_start()`
  resets GSP Falcon, flips BCR_CTRL = VALID|CORE_SELECT(RISC-V)|
  BRFETCH at 0x111668, hands off the libos arg pointer via
  MAILBOX0/1, releases reset via STARTCPU, polls RISCV_CPUCTL.ACTIVE
  (bit 7) for "RISC-V running".

- **Harness CLI** — `gsp-harness --booter-load` and
  `--riscv-start` run the full chain through each milestone with
  diagnostics dumped on failure.

**Tests landed:** 91 host-side unit tests across 5 suites

### E4. GSP-RM RPC message ring (P3-4) — **SKELETON SHIPPED**

**Shipped (worktree-x86-64-capstone-gap-work):**

- Shared core: `kernel/gpu/nvidia/rpc.{h,c}`. Single contiguous
  shared-memory region holding the head/tail pointer page plus
  cmdq + msgq (256 KB each, matching nouveau / openrm framing).
- Pure ring math (page sizing, modular pointer advance, full/empty
  disambiguation) implemented and unit-tested with 15 cases via
  `make test-rpc`. The tests cover wrap-around, exact-page edge
  cases, the "subtract one to disambiguate" rule, and the
  init/dtor pair against a mock platform vtable.
- `gsp_rpc_init()` / `gsp_rpc_dtor()` allocate the shm region and
  lay out the rings at the canonical offsets the GSP side expects
  (cmdq w/r at byte 0/4, msgq w/r at byte 0x100/0x104).
- `gsp_rpc_send()` / `gsp_rpc_wait()` — the framing-aware send and
  blocking poll. Returns ENOSYS (-1) until the channel sees
  GSP_INIT_DONE — without GSP-RM alive on the RISC-V core, the
  consumer never advances rptr and posting would silently fill
  the ring.

**Remaining hardware work (post-bringup):**

- Element-header + RPC-header marshalling into the cmdq pages.
- GSP_INIT_DONE polling loop in `gsp_rpc_wait()`.
- The subset of RPCs needed for matmul:
  - `NV_GSP_RPC_INIT` — hand off host-side layout info.
  - `NV_GSP_RPC_ALLOC_MEM` — carve out VRAM.
  - `NV_GSP_RPC_SUBMIT_COMPUTE` — enqueue a compute kernel.

**Original est.** 10 days; **actual:** ~3 hours for the skeleton
+ pure-logic tests; the hardware-dependent send/wait completion
remains.

## Exit criteria for "full support"

A gap is closed when:

- Its deliverables are committed and merged.
- Its listed tests pass in CI (QEMU) and on test-pc (real hardware)
  for every subsequent PR for 10 consecutive runs.
- `docs/x86-64-capstone-gaps.md` marks it CLOSED with a PR link.

When every P1-\*, P2-\*, P3-\* gap is marked CLOSED and the full
`make test PLATFORM=X86_64` test suite passes cleanly (no pre-existing
skips), preemptive multitasking, SMP, and GPU-backed model inference on
x86-64 are feature-complete.
