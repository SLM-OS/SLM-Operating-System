# ADR 0009: run the ARM64 hardware kernels at EL2 with VHE

Status: accepted (backfilled).

## Context

Until April 2026 SLM-OS could not run on Jetson Orin Nano: the Tegra234 CBB firewall answered peripheral accesses with a RAS error that EL3 turns into a core power-off, and the January record concluded that every bare-metal method was blocked (`3dc9c41d` 2026-01-15 "Update docs: Jetson CBB firewall blocks bare-metal access"). The archived bring-up note records that all peripheral accesses from EL1 were rejected (`docs/archive/investigations/jetson-el2-bringup.md`, Background). L4T Linux itself runs at EL2 with VHE, and kexec's `HVC_SOFT_RESTART` enters the next image at EL2 (same note; `docs/jetson-cbb-report.md` §3).

Pi 5 firmware also enters at EL2. Until May 2026 SLM-OS dropped to EL1 there, and NS-EL1 IRQ delivery on BCM2712 / GIC-400 did not work for any timer PPI (#672, #683; `docs/archive/plans/pi5-el2-vhe-plan.md`).

## Decision

On Jetson and Pi 5, the primary CPU (`kernel/arch/arm64/boot.S`) and every secondary (`kernel/arch/arm64/smp_boot.S`) stay at EL2 with `HCR_EL2.E2H=1, TGE=1, RW=1` (bits 34, 27, 31) whenever `CurrentEL` reads EL2. With E2H set, the kernel's `_EL1` system-register names reach the `_EL2` registers, so the MMU, vector and timer code is shared with the EL1 build.

- Jetson primary: read-modify-write of `HCR_EL2` (ORs in E2H|RW|TGE), after the UEFI path has turned the EL2 MMU off; then disables the inherited CNTP/CNTV/CNTHP timers and sets SPAN, clears PAN (#1079).
- Jetson and Pi 5 secondaries, and the Pi 5 primary: unconditional write of `HCR_EL2`; Pi 5 also clears `HSTR_EL2` and programs `CNTHCTL_EL2`.
- If firmware enters at EL1 the code falls through and runs at EL1. QEMU virt (no `virtualization=on`) enters at EL1 and runs there. x86-64 runs in ring 0, so the question does not apply.

On Jetson the EL2 permission set reaches UARTC (`0x0C280000`), the TCU RX mailbox, GICv3, the generic timer, the watchdog and GPU BAR0; UARTA (`0x03100000`) and the OP-TEE carveout stay blocked (`docs/jetson-boot.md` peripheral table; `docs/jetson-cbb-report.md` §1, §3).

## Alternatives considered

- **Run at EL1 on Jetson.** Tried before April 2026; peripheral accesses were rejected (`docs/archive/investigations/jetson-el2-bringup.md`). A later one-shot test, `kernel/tests/jetson_el1_smoke.S` (`JETSON_EL1_SMOKE`, `407d2ac8` 2026-04-17), drops to EL1 to compare PCIe/XHCI reads at the two levels.
- **Stay at EL1 on Pi 5 and fix IRQ delivery there.** Investigated in #672 and #134; IRQs did not deliver at NS-EL1 for any PPI. #683 moved Pi 5 to EL2 instead.
- **A hypervisor design.** Never considered: SLM-OS was meant to run on bare metal from the start (user, 2026-11-14).
- **EL2 without VHE (E2H=0).** E2H=0 pays off only with a separate kernel at EL1, which conflicts with the bare-metal intent and the planned user/kernel separation. VHE supports that separation directly: TTBR1_EL2 for the kernel, TTBR0_EL2 with ASIDs per process, EL0 exceptions taken at EL2 under `HCR_EL2.TGE=1`, and PAN/SPAN at EL2. Whether E2H=0 was ever tried is not recorded (user, 2026-11-14).
- **The four avenues past the CBB in `docs/jetson-cbb-report.md` §6** (BCT reconfiguration, NVIDIA secure boot chain, KVM passthrough, custom EL3 SMC service) are listed as future options, not as alternatives that were weighed for this decision.

## Consequences

- The same kernel source runs at EL2 on hardware and at EL1 in QEMU, so QEMU does not exercise the EL2 paths (HCR, CNTHCTL, VBAR_EL2 delivery). Hardware runs are the only check of them.
- Exceptions, including EL0 SVCs, are taken to EL2 (`TGE=1`); PR #698 added a vector-layout regression test for EL0 to EL2 SVC on Pi 5.
- Hardware quantum preemption on Pi 5 depends on this mode (PR #693 timer on PPI 26; PR #742).
- Peripherals the CBB blocks at EL2 stay out of reach; the UART console is UARTC through the TCU.
- Boot banner prints the live `CurrentEL` and `HCR_EL2.E2H` (`413774fc`).
- The `smp_boot.S` Jetson comment says it "matches Jetson primary CPU's unconditional overwrite", but the primary has used a read-modify-write since PR #245; the comment is stale.
