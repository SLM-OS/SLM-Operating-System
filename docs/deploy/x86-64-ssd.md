# Deploying SLM-OS to x86-64: UEFI Disk Image on an SDWire SD Card

This guide covers deploying SLM-OS to the lab's x86-64 target (`test-pc`): a Gigabyte H610M with i7-6700, 16 GB DDR4, and an RTX 3050. The deploy medium is an SD card behind an SDWire. The SDWire connects the card either to the lab host, for flashing, or to `test-pc`'s card reader, for booting, so a new image can be flashed and booted without moving anything by hand.

The boot chain is: **UEFI firmware → GRUB (embedded in the disk image) → multiboot2 → SLM-OS**.

(The file name is historical: an earlier setup used an external SATA SSD as the deploy medium.)

---

## When to use this guide

| Scenario | Guide |
|---|---|
| Lab `test-pc`, iterative SLM-OS deploy | This guide |
| Fresh x86-64 system, installing SLM-OS for the first time | This guide, plus an SDWire and the firmware settings below |
| x86-64 kexec from a running Linux | [WIP, see `docs/x86-64-gpu-inference-status.md` §4.2.k]; not yet a production deploy path |
| x86-64 QEMU | `make run PLATFORM=X86_64`; no deploy step, out of scope here |

## Prerequisites

| Item | Source / Version |
|---|---|
| `test-pc` with an SDWire feeding its SD card reader | An SDWire assigned to `test-pc` in labctl (labctl is the source of truth for which device) |
| Ubuntu on the external SSD (optional but useful) | The fallback boot when no bootable SD card is present (see Recover to Ubuntu). It has passwordless root key auth; `<TEST_PC_IP>` below is the address labctl reports for `test-pc`. |
| SLM-OS source checkout | `make kernel PLATFORM=X86_64` and `make x86-disk PLATFORM=X86_64` both succeed |
| x86-64 toolchain | `x86_64-linux-gnu-gcc` |
| `grub-mkimage`, `mtools` (`mformat`, `mcopy`, `mmd`), `sgdisk` | For building the UEFI disk image. No `sudo` / `losetup` required: `mtools` writes the FAT32 filesystem directly at the partition offset inside the GPT disk. `sgdisk` lives in `/usr/sbin`; if that is not on `PATH`, CMake silently disables the disk-image target (`x86 disk: disabled` in the configure output) |
| labctl access | With the SDWire, serial console and power plug configured for `test-pc` |

### Firmware (BIOS) settings

The flow below relies on these UEFI setup options on `test-pc`. A
hardware change (adding or moving a drive or card reader) can reset the
boot order or drop the machine into setup on the next power-on, so
recheck them after any physical change:

| Setting | Required value | Why |
|---|---|---|
| Boot priority | SD card reader first, external Ubuntu SSD second; the internal disk (old, dormant SLM-OS install) deselected | A power cycle boots SLM-OS when a bootable card is present; Ubuntu boots when it is not |
| CSM / legacy boot | Disabled (UEFI only) | `slmos-x86.img` is GPT with an EFI System Partition |
| Secure Boot | Disabled | The GRUB in the image is unsigned |
| Restore on AC power loss | Power On | A labctl plug power cycle must boot the machine without a power-button press |
| Onboard serial (COM) port | Enabled | SLM-OS and the labctl console use it |

UEFI offers a removable disk as a boot option only if it has
`\EFI\BOOT\BOOTX64.EFI` on a FAT partition. A card without that file
(for example a Raspberry Pi card) does not appear in the boot menu.

## Build the UEFI disk image

```bash
make x86-disk PLATFORM=X86_64
```

Outputs `build/kernel/slmos-x86.img`, a 128 MB GPT disk image with an EFI System Partition containing GRUB (multiboot2-capable) and the SLM-OS kernel. `make x86-disk-verify` runs a 9-check structural validator against the image; run it before deploying if the build system has been touched recently:

```bash
make x86-disk-verify PLATFORM=X86_64
```

## Flash and boot

### Step 1: Flash the image to the SD card

Use labctl's `flash_image` tool for `test-pc` with `slmos-x86.img`. It
powers `test-pc` off, switches the card to the host, writes the image,
and switches the card back. The image must be readable by labctl: an
uploaded image, or a path inside its allowed read paths (`list_images`
lists the options). A 128 MB write takes about 12 s on a healthy card.

### Step 2: Boot SLM-OS

Power `test-pc` on, or power-cycle it, through labctl. With the card first
in the boot order, UEFI hands off to GRUB on the card, GRUB loads SLM-OS
via multiboot2, and the `slmos>` prompt appears on serial about 15 s
after power-on.

For a reliability run, use labctl `boot_test` with the pattern `slmos>`
and no image (the card already holds the build).

### Step 3: Interact via serial

SLM-OS on `test-pc` has no working network interface. Its x86 network
drivers are virtio-net (QEMU only) and USB CDC-ECM; `test-pc`'s onboard
Ethernet has no driver, and no CDC-ECM device is attached. SSH is
therefore unavailable. All interaction goes through labctl's serial tools
(MCP `serial_send` / `serial_capture`; CLI `labctl serial send` /
`labctl serial capture`), or an interactive session with
`labctl connect test-pc`.

### Step 4: Recover to Ubuntu

Ubuntu boots whenever there is no bootable card in the reader. To get
back to Ubuntu without touching the card:

1. Power `test-pc` off through labctl.
2. Switch the SDWire to the host (MCP `sdwire_to_host`; CLI
   `labctl sdwire host test-pc`). `test-pc`'s reader
   now sees no card.
3. Power `test-pc` on. UEFI falls through to the external Ubuntu SSD; SSH
   (`ssh root@<TEST_PC_IP>`) is available about 30 s later.

Switch the card back to `test-pc` (MCP `sdwire_to_dut`; CLI
`labctl sdwire dut test-pc`; machine off)
before the next SLM-OS boot. A one-off Ubuntu boot is also available from
the firmware boot menu (F12) with the card left in place.

## Iterative development loop

1. `make kernel PLATFORM=X86_64 && make x86-disk PLATFORM=X86_64`
2. labctl `flash_image` for `test-pc` with the new image
3. labctl power on / power cycle `test-pc`
4. labctl `serial_capture` (CLI: `labctl serial capture test-pc --until "slmos>"`) until the prompt appears

## Troubleshooting

### The firmware boot menu does not list the SD card

- Check that the card holds the SLM-OS image: labctl `sdwire_info` should
  show a GPT disk with one FAT32 partition labelled `EFI` (flags
  `boot, esp`), and `sdwire_ls` should list `/EFI/BOOT/BOOTX64.EFI` and
  `/slmos/kernel.elf`.
- Check that the card is switched to `test-pc` (DUT), not the host.
- Check the firmware's card-reader setup, then the boot priority above.

### The host does not see a newly inserted card

The SDWire's host-side reader does not poll for media changes, so after a
card swap the kernel keeps reporting the previous card (or none). Switch
the SDWire to the DUT and back to the host through labctl; the
re-enumeration picks up the new card.

### `flash_image` hangs, or the kernel log shows write faults

`Sense Key: Medium Error`, `Peripheral device write fault` in `dmesg` for
the SDWire's block device means the card is rejecting writes; replace the
card. If a known-good card fails the same way, suspect the SDWire. At the
time of writing, `flash_image` has no write timeout, so a failing card
can hang the call until the client gives up.

### UEFI boots the card but GRUB → SLM-OS hand-off fails

Run the image validator first:

```bash
make x86-disk-verify PLATFORM=X86_64
```

All 9 checks should pass. If any fail, the disk image is malformed. If they pass and SLM-OS still doesn't boot, suspect a GRUB → multiboot2 regression; check recent changes under `kernel/arch/x86_64/` and `cmake/x86-disk.cmake`.

### GPU is bound to `vfio-pci` and SLM-OS can't touch it

Under Ubuntu, `test-pc` binds the RTX 3050 to `vfio-pci` by default for VFIO passthrough experiments (see `docs/testing/test-pc-linux-vfio-setup.md`). SLM-OS runs bare-metal, so VFIO only matters while Ubuntu is booted. To test `nouveau` for the SEC2-unlock path (see `docs/nvidia-gsp.md`):

```bash
ssh root@<TEST_PC_IP> 'rmmod vfio_pci; modprobe nouveau modeset=1'
```

`modeset=1` is required because `nouveau` is blacklisted in `/etc/modprobe.d/`; plain `modprobe nouveau` will fail with *"Exec format error"*.
