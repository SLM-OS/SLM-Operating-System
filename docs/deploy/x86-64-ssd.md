# Deploying SLM-OS to x86-64 — UEFI Disk Image on SDWire-flashed SSD

This guide covers deploying SLM-OS to the lab's x86-64 target (`test-pc`): a Gigabyte H610M with i7-6700, 16 GB DDR4, and an RTX 3050. The deploy medium is an external SATA SSD connected via SDWire, which lets the host flash a UEFI disk image without manually moving drives.

The boot chain is: **UEFI firmware → GRUB (embedded in the disk image) → multiboot2 → SLM-OS**.

---

## When to use this guide

| Scenario | Guide |
|---|---|
| Lab `test-pc` — iterative SLM-OS deploy | This guide |
| Fresh x86-64 system, installing SLM-OS for first time | This guide + set up SDWire + `efibootmgr` entry |
| x86-64 kexec from a running Linux | [WIP — see `docs/x86-64-gpu-inference-status.md` §4.2.k]; not yet a production deploy path |
| x86-64 QEMU | `make run PLATFORM=X86_64` — no deploy step, out of scope here |

## Prerequisites

| Item | Source / Version |
|---|---|
| `test-pc` with SDWire connecting an external SSD | `pc-sdwire` assigned to `test-pc` in labctl |
| Ubuntu installed on the built-in primary SSD (optional but useful) | Allows SSH recovery if the SDWire boot image fails. `test-pc` has Ubuntu at `192.168.4.136` with passwordless root key already set up. |
| SLM-OS source checkout | `make kernel PLATFORM=X86_64` + `make x86-disk PLATFORM=X86_64` both succeed |
| x86-64 toolchain | `x86_64-linux-gnu-gcc` |
| `grub-mkimage`, `mtools` (`mformat`, `mcopy`, `mmd`), `sgdisk` | For building the UEFI disk image. No `sudo` / `losetup` required — `mtools` writes the FAT32 filesystem directly at the partition offset inside the GPT disk. |
| labctl CLI or MCP access | With SDWire and power plug configured for `test-pc` |

## Build the UEFI disk image

```bash
make x86-disk PLATFORM=X86_64
```

Outputs `build/kernel/slmos-x86.img` — a GPT-partitioned disk image with an EFI System Partition containing GRUB (multiboot2-capable) and the SLM-OS kernel. `make x86-disk-verify` runs a 9-check structural validator against the image; worth running before deploy if the build system has been touched recently:

```bash
make x86-disk-verify PLATFORM=X86_64
```

---

## Flash and boot — full cycle

### Step 1 — Flash the image to the SDWire SSD

```bash
labctl sdwire flash --no-reboot test-pc build/kernel/slmos-x86.img
```

The `--no-reboot` flag leaves `test-pc` powered on after the flash completes so the UEFI boot order can be adjusted via SSH before rebooting.

**Known flakiness:** `labctl sdwire flash` sometimes errors with *"Block device not found after switching to host"* on the first attempt. Retry — it almost always succeeds on the second try. This is tracked upstream in labctl; no action required here.

### Step 2 — Tell UEFI to boot the SDWire SSD next

UEFI boot entries are indexed by `efibootmgr`. Indices are **not stable across reboots** — query them fresh every time:

```bash
ssh root@192.168.4.136 efibootmgr -v
```

Look for the entry whose `HD()` descriptor matches the SDWire SSD (typically a different GUID from the internal Ubuntu SSD, often labeled similarly to "UEFI OS" or the SDWire model string). Say the index is `0002`:

```bash
ssh root@192.168.4.136 efibootmgr --bootnext 0002
```

`--bootnext` is a one-shot: UEFI boots that entry on the next power-on, then reverts to the default order. This avoids permanently reconfiguring boot priority each deploy.

### Step 3 — Reboot into SLM-OS

```bash
labctl power_cycle test-pc
```

UEFI hands off to GRUB on the SDWire SSD, GRUB chainloads via multiboot2 into SLM-OS, and the `slm>` prompt should appear on serial within a few seconds.

### Step 4 — Interact via serial

While SLM-OS is running, **SSH does not work** — SLM-OS has no network stack on x86-64. All interaction is via labctl's serial tools:

```bash
labctl serial_send test-pc "<command>"
labctl serial_capture test-pc --timeout 30
```

Or for an interactive shell:

```bash
labctl connect test-pc-console
```

### Step 5 — Recover back to Ubuntu

The `--bootnext` entry is consumed on first boot, so a plain power cycle (`labctl power_cycle test-pc`) brings Ubuntu back on the next boot without manual intervention. Wait ~30 s, then SSH is available again:

```bash
ssh root@192.168.4.136
```

## Iterative development loop

For a tight development loop, the cycle is:

```bash
# Rebuild
make kernel PLATFORM=X86_64 && make x86-disk PLATFORM=X86_64

# Flash
labctl sdwire flash --no-reboot test-pc build/kernel/slmos-x86.img

# Re-arm bootnext (index changes between boots!)
BN=$(ssh root@192.168.4.136 efibootmgr -v | \
     grep -i 'sdwire\|UEFI OS' | head -1 | sed -E 's/^Boot([0-9A-F]+).*/\1/')
ssh root@192.168.4.136 efibootmgr --bootnext "$BN"

# Reboot
labctl power_cycle test-pc

# Watch
labctl serial_capture test-pc --timeout 60 --pattern "slm>"
```

`BN` detection is heuristic — adjust the `grep` pattern to match the actual boot entry label on `test-pc`. Once found, the extraction is stable for that power-on; only the index number changes across reboots.

## Troubleshooting

### `labctl sdwire flash` fails with "Block device not found after switching to host"

Retry. Known labctl flakiness — the SD-over-USB re-enumeration sometimes exceeds labctl's timeout. The flash itself is fine on the second attempt.

### `efibootmgr --bootnext` accepted but machine boots Ubuntu anyway

Almost always means the wrong index was selected. Re-check `efibootmgr -v` — the SDWire entry's `HD()` GUID should differ from the internal Ubuntu SSD. If they're similar-looking, use `blkid` / `lsblk` to identify which disk is the SDWire.

### UEFI boots the SDWire but GRUB → SLM-OS hand-off fails

Run the image validator first:

```bash
make x86-disk-verify PLATFORM=X86_64
```

All 9 checks should pass. If any fail, the disk image is malformed. If they pass and SLM-OS still doesn't boot, suspect a GRUB → multiboot2 regression — check recent changes under `kernel/arch/x86_64/` and `cmake/x86-disk.cmake`.

### GPU is bound to `vfio-pci` and SLM-OS can't touch it

`test-pc` is configured by default with the RTX 3050 bound to `vfio-pci` for VFIO passthrough experiments (see `docs/testing/test-pc-linux-vfio-setup.md`). SLM-OS runs bare-metal — VFIO isn't in the picture — but between deploys, Linux userspace is. To test `nouveau` for the SEC2-unlock path (see `docs/nvidia-gsp.md`):

```bash
ssh root@192.168.4.136 'rmmod vfio_pci; modprobe nouveau modeset=1'
```

`modeset=1` is required because `nouveau` is blacklisted in `/etc/modprobe.d/`; plain `modprobe nouveau` will fail with *"Exec format error"*.

### `efibootmgr` over serial asks for a password

It shouldn't — `efibootmgr` is only reachable from Linux userspace, and we already have passwordless root key auth via SSH. If it prompts, SSH in instead; don't try to drive Ubuntu via serial.
